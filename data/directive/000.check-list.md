#### 2. Modality Dispatcher (Dynamic Item Evaluation)
Evaluate each checklist item against one of the five execution modalities below:

##### Modality A: Fenced or Inline Shell Commands
* Applies to items declaring `* **Command:** <cmd>` or a multiline fenced block (`* **Command:** \n ```bash\n<cmd>\n``` `)[cite: 1, 2, 3].
* **Execution:**
  1. Execute the command from the repository root directory.
  2. Parse the exit status code, standard output (`stdout`), and standard error (`stderr`).
  3. Compare results against both `Observable Output` and `Observable Criteria`:
     - **Standard Success:** Expected exit code `0` with matching output text or line count[cite: 1, 2, 3].
     - **Negative Control / Invariant Sweeps:** Items checking clean git status, missing files, or absence of prohibited patterns (e.g., `git grep -n "debugger"` or `git grep -P "[\x{1F300}-\x{1FAD6}]"`) explicitly expect exit code `1` or zero matches[cite: 1, 2, 3]. Treat exit code `1` as **PASSED** if the observable specification designates zero matches as the success condition[cite: 1, 2, 3].
     - **Node.js Inline Scripts:** Inline script evaluations (e.g., `node -e "..."`) must execute under the local Node runtime and succeed with exit code `0` and matching terminal outputs[cite: 2, 3].
  4. If the exit code and output match the declared criteria, resolve to `[x]`; otherwise, resolve to `[-]`.

##### Modality B: Static Code & AST Inspection Targets
* Applies to items declaring `* **Inspection Target:** <path>` without an automated command, or items requiring code structure validation[cite: 1, 2, 3].
* **Execution:**
  1. Read the designated target file from disk.
  2. Evaluate the code against the stated criteria (e.g., checking for specific AST imports, re-exports, non-blocking asynchronous stubs, type union extensions, or batching latches like `setImmediate`)[cite: 1, 2, 3].
  3. Formulate and run a quick verification command (such as `git grep` or an inline Node/AST probe) to deterministically verify that the pattern exists.
  4. If the source file satisfies all criteria listed in the item, resolve to `[x]`; otherwise, resolve to `[-]`.

##### Modality C: Automated Test Runners (AVA / Vitest / npm)
* Applies to items invoking test runners (e.g., `npx ava <path> -m "<match>"`, `npm test`, `npm run check:types`, or `npm run check:all`)[cite: 1, 2, 3].
* **Execution:**
  1. Execute the test command directly from the monorepo root.
  2. Verify that test assertions pass with exit code `0` and match the expected runner report[cite: 1, 2, 3].
  3. If tests fail, crash, time out, or throw unhandled exceptions, resolve to `[-]`.

##### Modality D: Interactive Curses & TUI Walkthrough Safety
* Applies to items referencing interactive screens, curses key bindings, or live TUI execution (e.g., `npm run tui`)[cite: 1].
* **Execution:**
  1. **Do not run long-lived or blocking interactive processes** that hang standard input or curses screen buffers in headless mode.
  2. Verify interactive criteria headlessly:
     - Check the entry point source code, widget configurations, and keybinding registrations (e.g., vertical navigation keys `['up', 'k']` in choice units)[cite: 2].
     - Run the dedicated headless mock test suites (e.g., `openChoice -- handles headless environment cleanly`)[cite: 2].
  3. If the item cannot be verified via automated static analysis or headless unit tests, mark it `[-]` and record it as requiring manual curses validation.

##### Modality E: Markdown Verification Matrices & Tables
* Applies to summary verification tables (e.g., `Acceptance Criteria Verification Matrix`) containing `| Requirement | Target | Observable Pass Criteria | Status |`[cite: 2].
* **Execution:**
  1. Synchronize each table row's status (`| [ ] |` -> `| [x] |` or `| [-] |`) with the corresponding evaluated item from the preceding sections[cite: 2].
  2. For standalone table rows not paired with a section item, evaluate the `Observable Pass Criteria` directly against disk state.
