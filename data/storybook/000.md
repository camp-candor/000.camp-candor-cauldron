Relational Data Model & Dependency PinningThe ledger acts as a software build system (like make or Bazel) for narrative continuity using three core entities:   Fact Nodes (facts table): Atomic narrative claims containing id, claim_text, scope (CHARACTER, LOCATION, LOGISTIC, LAW), author, timestamp, and a strictly increasing version integer (NEW.version > OLD.version).   Scene Nodes (scenes table): Linear prose containers holding id, episode_num, scene_num, text, and certification status (clean, dirty, reviewed).   Dependency Edges (scene_fact_dependencies table): Junction records binding a scene_id to a fact_id, an entity_type (CHECK(entity_type IN ('character', 'location', 'possession', 'grievance', 'axiom'))), and the exact pinned_version (or fact_version) integer active when the scene was authored.   





The Deletion Principle: If every neural network weight, prompt history, generative isolate, and GPU server were permanently destroyed, the fictional universe—every character wound, inventory item, geographic coordinate, debt, and unresolved secret—remains 100% logically consistent and mathematically intact within the relational facts ledger. Conversely, if the facts ledger is lost, the universe suffers immediate "brain death," even if the models continue generating pixels and prose.


the foundational continuity mechanism of the entire pipeline reduces to three relational components:   A flat table of canonical narrative facts registering the somatic states of actors, inventory holdings, spatial topologies, and secrets.   A table of scenes with pinned dependencies on those facts (scene_fact_dependencies).   A dependency query and trigger that flags downstream scenes as dirty (is_dirty = 1 / status = 'DIRTY') whenever an underlying fact version increments.
