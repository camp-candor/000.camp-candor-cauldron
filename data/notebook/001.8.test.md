# End-to-End Integration Test Suite: State Mutation Logic

**Context:**
The helper functions `getPlayer`, `getMonster`, and `updateEntity` are the primary interface for all game logic to interact with the persistent state. An E2E test suite must verify that when a high-level game action (like an API call to `/attack`) invokes these helpers, the state changes are correctly applied, persisted, and visible to subsequent API calls. This proves the integration between the logic layer and the data layer is sound.

---

### **Test Case 1: `integration_Combat_Damage_Flow`**

- **Type:** Happy Path Integration
- **Context:** Verifies the full chain: API Request -> Logic -> `updateEntity` -> State Change.
- **The 'Red' State (Failure):**
  - **Scenario:**
    1. Send POST `/api/action` with payload `{ type: "ATTACK", damage: 5 }`.
    2. Query `GET /api/state`.
  - **Failure:** The response shows HP is unchanged (10). This means `updateEntity` failed to merge the new data or wasn't called correctly.
  - **Assertion Error:** `Expected HP 5, received 10.`
- **The 'Green' State (Success):**
  - **Logic:** Execute the attack. Inspect the global state object.
  - **Result:** The target entity's HP property reflects the subtraction.

### **Test Case 2: `integration_Entity_Lookup_Performance`**

- **Type:** Performance / Load
- **Context:** `getPlayer` and `getMonster` are called on every single interaction. They must be O(1) lookups to support real-time play.
- **The 'Red' State (Failure):**
  - **Scenario:** Populate state with 1000 monsters. Call `getMonster` 1000 times in a loop.
  - **Failure:** The operation takes > 100ms, indicating a linear search (array iteration) instead of a hash map lookup.
  - **Assertion Error:** `Lookup latency exceeded budget.`
- **The 'Green' State (Success):**
  - **Logic:** Benchmark the helper access time.
  - **Result:** Access time remains constant regardless of dataset size.

### **Test Case 3: `integration_Invalid_ID_Safety`**

- **Type:** System Stability
- **Context:** Malformed or malicious requests might pass invalid IDs to these helpers. The system must not crash.
- **The 'Red' State (Failure):**
  - **Scenario:** Send API request targeting ID `undefined` or `null`.
  - **Failure:** The server process crashes with `TypeError: Cannot read property of undefined` inside `updateEntity`.
  - **Assertion Error:** `Server crashed / 500 Error.`
- **The 'Green' State (Success):**
  - **Logic:** The helper functions catch the invalid ID, return `null` or `false`, and the API layer returns a graceful 400 or 404 error.
  - **Result:** The server remains online.

### **Test Case 4: `integration_Concurrent_Updates`**

- **Type:** Concurrency
- **Context:** Two players attack the same monster at the exact same millisecond. `updateEntity` must handle this without race conditions overwriting data.
- **The 'Red' State (Failure):**
  - **Scenario:**
    1. Request A: `updateEntity(id, { hp: current - 5 })`
    2. Request B: `updateEntity(id, { hp: current - 5 })`
  - **Failure:** Final HP is 5 (only one hit counted) instead of 0.
  - **Assertion Error:** `Expected HP 0, received 5.`
- **The 'Green' State (Success):**
  - **Logic:** Since Node.js is single-threaded, `updateEntity` is synchronous. Verify that the logic reads the _current_ state at the moment of execution, not the state at the start of the request.
  - **Result:** Both damage instances are applied sequentially.
