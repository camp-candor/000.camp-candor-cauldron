Setting up an MMORPG architecture on Cloudflare Durable Objects (DO) is a high-performance choice because it allows you to maintain state at the edge with low latency.

Here is a comprehensive architectural blueprint to set this up, including the folder structure, communication patterns, and a robust CI/CD pipeline.

---

### 1. Project Architecture & Structure

Since you have ~20 Durable Objects, you should use a **Monorepo** approach. This allows your Next.js frontend and your Workers/DO backend to share TypeScript types (critical for an MMO).

**Recommended Stack:**

- **Backend:** Cloudflare Workers + Durable Objects.
- **Storage:** R2 (for assets/save-state backups) + DO Storage (for active state).
- **Frontend:** Next.js (Deployed on Cloudflare Pages for proximity).
- **Tooling:** `wrangler`, `vitest` (for testing), `turborepo` (optional, for monorepo management).

#### Folder Structure

```text
/my-mmo
  /apps
    /web          # Next.js App
    /server       # Cloudflare Worker & DOs
      /src
        /objects  # Individual DO classes (Player, Room, Combat, etc.)
        index.ts  # Main Worker Entry
      wrangler.toml
  /packages
    /types        # Shared TS interfaces (PlayerStats, MessageTypes)
  .github/workflows
    deploy.yml
```

---

### 2. Organizing the Durable Objects

With 20+ DOs, you don't want a single massive file. Define each DO in its own file and export them from a central point.

**`apps/server/wrangler.toml`**

```toml
name = "mmo-backend"
main = "src/index.ts"
compatibility_date = "2024-01-01"

[[durable_objects.bindings]]
name = "PLAYER_DO"
class_name = "PlayerObject"

[[durable_objects.bindings]]
name = "WORLD_DO"
class_name = "WorldObject"
# ... repeat for all 20

[[r2_buckets]]
binding = 'ASSETS'
bucket_name = 'mmo-assets'
```

---

### 3. Communication Strategy

- **Client to DO:** Use WebSockets. The main Worker acts as a router that upgrades the connection and passes it to the specific Durable Object instance.
- **DO to R2:** Use R2 for "Cold Storage." Every 5 minutes or on logout, have the Player DO snapshot its state as a JSON blob to R2. This prevents data loss if a DO is evicted.
- **DO to External Next.js:** Use standard `fetch`. However, for performance, try to keep game logic inside the DOs and use the Next.js server only for Auth, Leaderboards, or the Website.

---

### 4. Testing Strategy (Crucial for MMOs)

Testing Durable Objects is tricky because they are stateful. Use **Vitest** with the official Cloudflare integration.

**Unit Tests (`src/objects/Player.test.ts`):**
Test the internal logic of the DO (e.g., XP calculation) without a network.

**End-to-End Tests:**
Use `miniflare` or the `unstable_dev` API in Wrangler to spin up a local version of your entire stack and simulate a WebSocket client joining a game.

---

### 5. The CI/CD Pipeline (GitHub Actions)

You need a workflow that runs tests first and only deploys if they pass. You will need a `CLOUDFLARE_API_TOKEN` stored in GitHub Secrets.

**`.github/workflows/deploy.yml`**

```yaml
name: CI/CD

on:
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm install

      # Run Unit & E2E Tests
      - run: npm run test

  deploy:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Deploy Worker
        uses: cloudflare/wrangler-action@v3
        with:
          apiToken: ${{ secrets.CLOUDFLARE_API_TOKEN }}
          workingDirectory: 'apps/server'

      - name: Deploy Next.js (if using CF Pages)
        uses: cloudflare/wrangler-action@v3
        with:
          apiToken: ${{ secrets.CLOUDFLARE_API_TOKEN }}
          command: pages deploy apps/web/out --project-name=mmo-web
```

---

### 6. Critical Scaling Tips for your MMO

1.  **Durable Object Hibernation:** Use the `state.setWebSocketHandler()` API. This allows your DOs to "sleep" while players are connected but idle, drastically reducing costs.
2.  **ID Mapping:** Use `idFromName(roomName)` for world instances. This ensures that every player joining "North-Forest" hits the exact same DO instance.
3.  **R2 Throughput:** Cloudflare R2 is great, but don't save to it every time a player moves. Batch your saves.
4.  **External Next.js Auth:** Since your Next.js server is external, use **JWTs (JSON Web Tokens)**. Next.js signs the JWT on login; the Worker/DO verifies the signature using a shared secret. This avoids a slow API call from the DO to Next.js for every request.

3.  Set up **Vitest** for local testing using the Cloudflare environment.
4.  Configure the `wrangler.toml` with all 20 bindings and R2.
5.  Link your GitHub repo to the **Wrangler Action** for automated deployments.

Here is the 2025 production-ready setup for a multi-Durable-Object (DO) architecture with automated GitHub deployment.

---

### 1. The "World Instance" Architecture

With ~20 Durable Objects, you likely have different "Systems" (Combat, Chat, Inventory, World Tiles). For an MMO, you want to shard players across instances to avoid bottlenecks.

**`apps/server/wrangler.toml`**
Starting Dec 2024/Jan 2025, **SQLite-backed Durable Objects** are the standard. They provide 10GB of storage and support SQL queries directly inside the DO.

```toml
name = "mmo-backend"
main = "src/index.ts"
compatibility_date = "2025-01-01"

# Define all 20 classes here
[[durable_objects.bindings]]
name = "ROOMS"
class_name = "RoomObject"

[[durable_objects.bindings]]
name = "PLAYERS"
class_name = "PlayerObject"

# Use the new SQLite backend for high-performance state
[[durable_objects.bindings]]
name = "COMBAT_ENGINE"
class_name = "CombatObject"

# R2 for cold storage / assets
[[r2_buckets]]
binding = "GAME_ASSETS"
bucket_name = "mmo-r2-storage"
```

### 2. Implementation: WebSocket Hibernation

In a standard DO, if a player goes to get a coffee, the DO stays "awake" and charges you. In a Hibernatable DO, it serializes state and "sleeps" while the TCP connection stays open on Cloudflare's edge.

**`apps/server/src/objects/RoomObject.ts`**

```typescript
import { DurableObject } from 'cloudflare:workers';

export class RoomObject extends DurableObject {
  constructor(ctx: DurableObjectState, env: Env) {
    super(ctx, env);
    // Recover state when DO wakes up
    this.ctx.getWebSockets().forEach((ws) => {
      const meta = ws.deserializeAttachment(); // Recover player ID, position, etc.
    });
  }

  async fetch(request: Request) {
    const webSocketPair = new WebSocketPair();
    const [client, server] = Object.values(webSocketPair);

    // 1. Accept and Hibernate
    this.ctx.acceptWebSocket(server);

    // 2. Attach data to the socket so we know who this is when it wakes up
    server.serializeAttachment({ playerId: 'player_123', lastActive: Date.now() });

    return new Response(null, { status: 101, webSocket: client });
  }

  // This is called when a message arrives, even if the DO was sleeping!
  async webSocketMessage(ws: WebSocket, message: string) {
    const data = ws.deserializeAttachment();
    // Logic: Broadcast to other players in the room
    this.ctx.getWebSockets().forEach((otherWs) => {
      if (otherWs !== ws) otherWs.send(`${data.playerId}: ${message}`);
    });
  }
}
```

### 5. Connecting to External Next.js Server

Since your Next.js server is external, you face a latency penalty if you call it for every game action.

1.  **Auth Handshake:** Next.js issues a **JWT** when the player logs in.
2.  **WebSocket Connection:** The player sends the JWT in the first WebSocket message (or as a query param).
3.  **DO Verification:** The Durable Object verifies the JWT locally using a shared `AUTH_SECRET`. **Do not** fetch the Next.js server to verify sessions on every message.
4.  **Async Syncing:** If you need to save player progress to the external Next.js database, use a **Durable Object Alarm**.
    - The DO updates its local SQLite storage immediately.
    - It sets an alarm for 30 seconds later to "bulk sync" the last 30 seconds of data to your external server via a single POST request.

### Key Checklist for Success:

- **Monorepo:** Use `pnpm` or `npm` workspaces so your Next.js app and DOs share the same `types.ts` file.
- **Alarms:** Use `this.ctx.storage.setAlarm()` for any logic that needs to happen even if players disconnect (e.g., world regeneration, auction house expiry).
- **RPC:** Use **Durable Object RPC** (new in 2024) to let your Worker call DO methods directly (e.g., `await stub.getPlayerStats()`) instead of using internal `fetch` calls. This is significantly cleaner and faster.

### 1. The "Atom of Coordination" Pattern

In an MMO, don't think of DOs as "services" (e.g., one huge "Combat DO"). Think of them as **Entities**. Cloudflare's new 2025 best practices emphasize "one Durable Object per logical unit."

- **World Instances:** Instead of one `WorldDO`, have one instance of `RoomObject` per map tile or dungeon.
- **Players:** Each player should have their own `PlayerObject` instance to manage their inventory and stats.
- **Combat:** A `CombatObject` instance is created per battle/encounter.

**Organizational Tip:** Even with 20 _types_ (classes) of DOs, you will have _millions_ of instances. Organize your types by "domain" in your folder structure:

```text
src/
  ├── gateway.ts        # Entry point (Worker)
  ├── objects/
  │   ├── core/         # Critical infra DOs
  │   │   ├── Player.ts
  │   │   └── Auth.ts
  │   ├── world/        # Spatial DOs
  │   │   ├── Room.ts
  │   │   └── Instance.ts
  │   └── systems/      # Game mechanics DOs
  │       ├── Combat.ts
  │       ├── Trade.ts
  │       └── Auction.ts
```

### 2. Configuration Management (`wrangler.jsonc`)

In 2025, Cloudflare recommends `wrangler.jsonc` (JSON with comments) over `.toml` for better tooling support. Managing 20+ bindings in one file is bulky, so use clear naming conventions.

**`wrangler.jsonc` snippet:**

```jsonc
{
  "name": "mmo-backend",
  "durable_objects": {
    "bindings": [
      // Format: { "name": "BINDING_NAME", "class_name": "ClassName" }
      { "name": "PLAYERS", "class_name": "PlayerObject" },
      { "name": "ROOMS", "class_name": "RoomObject" },
      { "name": "COMBAT", "class_name": "CombatObject" },
      // ... 17 more
    ],

  "migrations": [
    {
      "tag": "v1",
      "new_sqlite_classes": ["PlayerObject", "RoomObject", "CombatObject"],
      // ^ Use SQLite for high-performance game state
    },
  ],
}
```

### 3. The "Gateway" Router (Ingress)

Since you have 20+ DOs, your `index.ts` (the Worker) should be a lightweight **Gateway**. Its only job is to look at a request and hand the WebSocket to the correct DO.

**`src/gateway.ts`**

```typescript
import { PlayerObject } from "./objects/core/Player";
// Import all 20 classes...

export default {
  async fetch(request, env) {
    const url = new URL(request.url);
    const path = url.pathname.split("/"); // e.g. /room/north-castle

    switch (path[1]) {
      case "room":
        return env.ROOMS.get(env.ROOMS.idFromName(path[2])).fetch(request);
      case "player":
        return env.PLAYERS.get(env.PLAYERS.idFromName(path[2])).fetch(request);
      default:
        return new Response("Invalid System", { status: 404 });
    }
  }
};

// Crucial: Export all classes for Wrangler to see
export { PlayerObject, RoomObject, ... };
```

### 4. Inter-Object Communication: RPC Pattern

This is the most critical organizational shift. In the past, DOs talked to each other via internal `fetch()` calls (HTTP). **Now, you use RPC.** This allows you to call methods on other DOs as if they were local functions.

**Example: A Combat DO needs to damage a Player DO**

```typescript
// src/objects/systems/Combat.ts
export class CombatObject extends DurableObject {
  async processAttack(targetPlayerId: string, damage: number) {
    // 1. Get a "stub" for the player
    const playerStub = this.env.PLAYERS.get(this.env.PLAYERS.idFromName(targetPlayerId));

    // 2. Call a method DIRECTLY on the other DO (RPC)
    // No JSON serialization or fetch boilerplate needed!
    const remainingHp = await playerStub.takeDamage(damage);

    return remainingHp;
  }
}
```

### 5. Shared Base Class

With 20 DOs, you’ll repeat a lot of logic (R2 backups, auth logging). Create a `BaseObject.ts` that your game objects extend.

```typescript
// src/objects/BaseObject.ts
import { DurableObject } from 'cloudflare:workers';

export abstract class BaseObject extends DurableObject {
  // Common logic for all 20 DOs
  async saveToR2(bucket: R2Bucket, key: string) {
    const data = await this.ctx.storage.get('state');
    await bucket.put(key, JSON.stringify(data));
  }
}
```

### Summary of Workflow for adding a new DO:

1.  **Create file:** `src/objects/NewSystem.ts`.
2.  **Add binding:** In `wrangler.jsonc`.
3.  **Export class:** In `src/gateway.ts`.
4.  **Run `npx wrangler types`**: This automatically updates your `Env` interface so `this.env.NEW_SYSTEM` becomes type-safe across your whole project.

This structure keeps your code **modular**, ensures **low-latency** communication via RPC, and makes **unit testing** easier because you can test each DO class in isolation.

describe('MMO Join Flow', () => {
  it('should allow a client to connect and receive a welcome message', async () => {
    // 1. Create a mock WebSocket client
    const webSocketPair = new WebSocketPair();
    const [client, server] = Object.values(webSocketPair);

    // 2. Simulate the 'Join' request to your Worker
    // This triggers your index.ts -> routes to the specific DO

      headers: {

        Authorization: 'Bearer mock-jwt-token',

      // Pass the server-side of the socket to the worker
      webSocket: server,
    });

    // 3. Verify the handshake succeeded (Status 101 Switching Protocols)
    expect(response.status).toBe(101);
    expect(response.webSocket).toBeDefined();

    // 4. Set up a listener on our 'client' side of the socket

### 4. Simulating Multiple Interacting Clients

To test if your DO is correctly broadcasting state (the core of an MMO), you can simulate two clients simultaneously in one test.

it('should broadcast movement from Player A to Player B', async () => {

### 2. Playwright vs. Vitest Pool Workers

Since you have 20+ Durable Objects, the choice depends on _what_ you are testing.

| Feature            | Playwright (Outside-In)                                         | Vitest Pool Workers (Inside-Out)                                       |
| :----------------- | :-------------------------------------------------------------- | :--------------------------------------------------------------------- |
| **Realism**        | **Highest.** Tests real browser WebSocket implementation.       | **High.** Uses the real `workerd` runtime but simulated clients.       |

| **Speed**          | **Slower.** Requires starting full servers and browser engines. | **Extremely Fast.** Runs in-process with hot-reload.                   |
| **DO Alarms**      | **Hard.** You have to wait for real time to pass.               | **Easy.** Can use `ctx.runAlarms()` to trigger logic instantly.        |
| **Cross-System**   | **Excellent.** Tests Next.js + Worker + DO together.            | **Limited.** Best for testing the Worker/DO in isolation.              |

### 3. The "Hybrid" Recommendation

For an MMORPG with 20 Durable Objects, **do not choose just one.**

- **Logic Heavy DOs:** Testing your Combat DO formulas (e.g., "Does a level 5 fireball do 20 damage?").

- **Concurrency:** Testing that when 10 browsers connect to one DO, the DO doesn't lag or drop messages.

- **Visual Sync:** Testing that the "Smoothing/Interpolation" on your frontend correctly handles the 20hz tick rate from the DO.
